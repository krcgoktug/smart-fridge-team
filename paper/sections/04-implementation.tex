\section{Implementation}
\label{sec:implementation}

This section reports the implementation in the order data flows
through the system: hardware (Section~\ref{sec:impl-hw}), sensor-node
firmware (Section~\ref{sec:impl-fw}), USB-to-HTTP bridge
(Section~\ref{sec:impl-bridge}), ESP32-CAM firmware
(Section~\ref{sec:impl-cam}), and the cross-platform Flutter
application (Section~\ref{sec:impl-app}).

\subsection{Hardware Configuration}
\label{sec:impl-hw}

The hardware platform comprises an Arduino Uno (ATmega328P, 16\,MHz)
on a perforated breadboard, a single HX711 module mounted on the same
breadboard, four 50\,kg-rated load cells at the four corners of a
47\,$\times$\,36\,cm cabinet shelf, a DHT11 mounted on the inner
upper wall, an MQ135 module mounted on the inner lower wall, and an
AI Thinker ESP32-CAM secured to a 3D-printed bracket on the
front-left edge of the cabinet, oriented downward. A 12\,V LED strip
(SMD 5050 pitch) lines the inner cabinet edges and is switched by a
MOSFET driven from D9. Table~\ref{tab:wiring} summarises pin
assignments. All sensors share a common 5\,V supply rail and ground.
The ESP32-CAM is powered independently through its programmer header
to isolate its higher transient current draw from the
microcontroller.

\subsection{Sensor-Node Firmware}
\label{sec:impl-fw}

The Arduino sketch executes a deterministic three-second sampling
loop. Each cycle reads the DHT11 through the \texttt{DHT.h} library
with NaN-tolerant retry, the MQ135 through 30-sample analog averaging
with a baseline subtraction performed during the first 30\,s after
boot, and the HX711 through the \texttt{HX711\_ADC} library using a
calibration factor of 20.626 derived from a single-purpose
calibration sketch. The combined state is composed into a
human-readable block, followed by the single-line JSON record that
the bridge consumes.

A short command parser running on \texttt{Serial.available()}
recognises the single-character commands \texttt{t}/\texttt{T} (tare
the HX711), \texttt{g}/\texttt{G} (re-baseline the MQ135), and
\texttt{l}/\texttt{L} (toggle the LED strip). These commands reach
the firmware indirectly: the mobile application issues HTTP
\texttt{POST} requests to the bridge, which forwards a single byte to
the serial port.

\subsection{USB-to-HTTP Bridge}
\label{sec:impl-bridge}

The bridge is implemented in pure Python on top of the standard
library and the \texttt{pyserial} package. It targets Windows, macOS,
and Linux without further dependencies.

On startup, the bridge inspects the output of
\texttt{serial.tools.list\_ports.comports()} and selects the first
port whose description matches a CH340 USB-serial adapter, or accepts
an explicit \texttt{--port} argument. Two threads operate in parallel:

\begin{enumerate}
  \item A reader thread performs blocking \texttt{readline()} calls,
        parses each JSON line, validates the schema, and atomically
        updates a shared \texttt{STATE} record protected by a mutex.
  \item An HTTP thread runs a \texttt{ThreadingHTTPServer} on port
        8787 and serves \texttt{GET /sensors}, \texttt{POST /tare}, and
        \texttt{POST /recalibrate\_gas}. Responses carry the
        \texttt{Access-Control-Allow-Origin: *} header so that the
        Flutter web build can poll the endpoint from a different
        origin.
\end{enumerate}

\texttt{POST} requests are acknowledged immediately rather than
waiting for the next sensor cycle, which avoids holding the HTTP
connection across the three-second sampling period.

\subsection{ESP32-CAM Firmware}
\label{sec:impl-cam}

The ESP32-CAM firmware initialises the OV2640 sensor in JPEG mode,
joins the local Wi-Fi using credentials supplied through a
git-ignored \texttt{cam\_secrets.h} header, prints its assigned IP
address on the serial monitor, and starts two independent
\texttt{esp\_http\_server} instances. Port 80 hosts the project's
status page and the \texttt{/capture} endpoint that returns a single
JPEG. Port 81 hosts the \texttt{/stream} endpoint that emits an MJPEG
live stream using the Espressif boundary header.

The Dashboard subscribes to \texttt{/sensors} through a one-second
\texttt{Stream.periodic} timer, rebuilds the four sensor cards on
each update, and exposes a \emph{Tare scale} button that issues a
\texttt{POST /tare} via the bridge. The Camera screen displays the
ESP32-CAM stream through a platform-specific widget---an
\texttt{Image.network} poll on the web target and an HTTP-MJPEG
streaming widget on the Android target---and forwards the
corresponding JPEG capture to the multi-QR routine described in
Section~\ref{sec:algo-qr}. The Products screen renders the in-memory
product list, with a per-item card whose status band colour reflects
the days remaining until expiration. The Alerts screen aggregates
the alert engine's output, which is rule-based:
the bridge being unreachable for ten seconds, a product expiring
within three days, a gas value departing sharply from the smoothed
baseline, and a temperature exceeding a configurable threshold each
generate an alert. The Settings screen lets the user record the
bridge URL and ESP32-CAM IP address; the displayed Firebase status of
\emph{Not configured} reflects the intentional in-memory operation
mode of the demonstration build.
